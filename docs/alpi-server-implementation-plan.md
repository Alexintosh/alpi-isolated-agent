# Alpi Server implementation plan

**First release outcome.** From the operator’s existing T3 Code installation, a coordinator pairs with a separate Linux PC, creates two isolated workspaces, assigns a real coding task to a guest agent using a local model, follows the task, joins the same workspace interactively and retrieves the verified result. The Linux service owns the VMs, Iron Proxy, credentials and job state. The laptop may disconnect during a run. Alpi Desktop stays closed throughout acceptance.

**Status.** Proposed design against Alpi revision `053422fe69eceb2d6a7772c98cdf4eb612d27318`. Commands and API shapes below are proposed interfaces. The initial reference target is one systemd Linux x86-64 host with working KVM. Record the actual distribution, architecture, disk, RAM, available inference endpoint and T3 provider configuration during deployment. ARM64 can use the same contracts once its full artifact set and live acceptance pass.

## 1. Product boundaries

| Component | Owns | Connection |
| --- | --- | --- |
| Linux `alpi-server` | Sandbox identities, resource admission, engine selection, job journal, retention, artifacts and authorization | Private HTTPS API for clients and a host-local operator socket |
| Engine adapter | VM lifecycle, guest execution and file I/O, resource limits, network attachment and ownership checks | Private host-side interface. Start with BoxLite and qualify Microsandbox independently |
| Host network and credential services | Per-sandbox Iron policy, trust roots, restricted inference relay, credential use and approval decisions | Bound to a particular sandbox and its current launch |
| Guest profile | Linux userland, tools and an optional agent. Pi and OpenCode are distinct harness selections. Model provider and model ID are separate fields | Guest process/session API and authenticated terminal access |
| Client | Pairing, project-scoped API calls, workspace transfer and human attachment | One portable `alpi` CLI with a stdio MCP mode. T3, standalone Codex and Claude Code can launch the same adapter |

A host is a machine running Alpi Server. A sandbox is one VM on that host. A profile is an operator-published template and set of allowed capabilities. A job is a unit of work inside a sandbox. Multiple jobs may share a persistent workspace when explicitly requested. Independent writers get separate workspaces by default.

For a later interactive profile, run **T3 headless inside a guest**. Its terminal, providers and projects belong to that guest. The outer coordinator retains its Alpi credentials. First-release T3 connectivity is simpler: the coordinator already running in T3 uses the Alpi MCP tools. A job accepted by this MCP yields an Alpi job ID. Native T3 child threads and pairing a guest as a T3 environment are separate integrations. [T3 remote environments](https://github.com/pingdotgg/t3code/blob/main/docs/user/remote-access.md) · [T3 Pi provider](https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-pi.md)

## 2. Repository and extraction

Add independently buildable packages under `packages/alpi-server/` and `packages/alpi-client/`, a Linux service unit under `deploy/linux/`, and a new `skills/alpi-server/SKILL.md`. Keep the desktop project at its current root. For the first release use the existing Node 24/CommonJS implementation and expose a Unix executable through a package `bin` entry. Declare Node 24 as the reference installer prerequisite. Publish server and client tarballs from clean staging directories with their own production dependency closures. A Linux installation must succeed without installing Electron, checking out this repository or resolving a package through a developer’s workspace symlink.

## 3. Small installer and upstream packages

Ship the Alpi executable, CLI, service definition, trusted release manifest and required licenses as a small control package. Iron, the VM engine and guest images are separately versioned packages. `alpi-server runtime install --engine boxlite --profile pi-dev` resolves just the dependency set for that host and profile. The portable client downloads no VM payload. Startup uses the activated set on disk. Downloads happen during an explicit install or update, outside the guest network.

1. **Declare each dependency.** A release manifest records component, release tag, supported OS/architecture, official publisher, exact asset URL, compressed bytes and SHA-256, expected extracted paths, file hashes and modes, license and compatibility tuple. Pin OCI images by digest. The trusted Alpi release carries the pins. Upstream signatures or attestations, when published for the selected release, are checked against a pinned release identity during release preparation. Use versioned Alpi release manifests for updates.
2. **Fetch the selected assets.** For the current Iron protocol, upstream publishes `iron-proxy_0.56.0_linux_amd64.tar.gz` and a distinct ARM64 archive. Validate the downloaded archive and inner executable against the release manifest before activation. Reuse `acquireArtifact` for HTTPS, bounded streaming and hash verification. Restrict redirects to the approved publisher’s release delivery hosts. GitHub-generated download URLs may expire, so keep the stable release asset URL in the manifest. Apply the same mechanism to the selected engine, helper binaries and guest profile packages. [Iron release assets](https://github.com/paradigmxyz/iron-proxy/releases/expanded_assets/v0.56.0)
3. **Stage, verify, activate.** The existing installer’s `prepare` expects a local package directory. Build a verified staging directory from the resolver’s package list, then reuse its verification and atomic selection pattern with a server-specific manifest. Cache artifacts by digest. Use a host file lock shared by all installer processes, bounded extraction, disk admission and separate active/previous receipts. Reinstallation with an intact cache must succeed offline. A failed download or hash mismatch preserves the active set.
4. **Upgrade deliberately.** Pin running sandboxes to their resolved engine, Iron and image revisions. Drain affected sandboxes before switching a non-coexistent component. Rollback selects the prior verified set while preserving project data. Reclaim old files only after checking references from the active set, rollback set and retained sandboxes. If an official compatible package is missing, report the component and platform during preflight. Any build-from-source distribution gets its own reviewed manifest.

**Release evidence:** list the contents, download hosts and sizes of the control package and the selected runtime set. Check a clean installation, cached reinstall, interrupted transfer, corrupted cache and rollback. Report installer download time separately from sandbox startup time.

## 4. Pairing and permissions

Adopt the T3 interaction pattern: a short-lived, single-use invitation created by the operator, a named client, an explicit access level and independent revocation. Alpi owns its protocol and credentials. [T3 pairing and access](https://github.com/pingdotgg/t3code/blob/main/docs/user/remote-access.md) · [T3 client enrollment](https://github.com/pingdotgg/t3code/blob/main/docs/user/outside-agents.md)

1. On first init, generate a stable server UUID and TLS identity. Bind management to loopback by default. The operator can configure a private address with TLS, or reach the loopback endpoint via an SSH tunnel. Bind the local administration socket to a private directory with operator-only access. Generate a separate Iron CA for guest traffic.
2. From the Linux console or an authenticated SSH session, the operator runs `alpi-server pair issue --project demo --role runner --expires 5m`. Display privately a 256-bit random single-use invitation, the expected server certificate fingerprint, server ID and address. Store a digest of the invitation with its expiry, project and maximum role. Deliver this information through the trusted operator channel. The prompt, command line, MCP configuration and logs should contain no invitation secret.
3. On the laptop, `alpi pair --name gaming-pc` accepts the enrollment details through a hidden prompt or protected input file. Verify the TLS identity against the out-of-band fingerprint **before sending the invitation**, then verify the server ID. The client exchanges at `POST /v1/pair/exchange`. A transaction consumes the invitation and creates a project-scoped client record. Return a 256-bit opaque bearer credential once over the authenticated channel. Start the pilot with a 30-day maximum client lifetime and an explicit re-enrollment flow.
4. Store only the credential digest, expiry, role, project and revocation state on the server. The client stores its credential in the OS credential store, or an explicitly configured encrypted headless store. Its named context carries address, server ID, fingerprint and credential reference. Rate-limit enrollment and authentication failures. On a lost exchange reply the operator can see and revoke the incomplete enrollment and issue a fresh invite. How to recover is part of CLI output.
5. List/revoke clients and rotate credentials from the local admin socket. Apply revocation to open streams and new requests. A changed server identity requires operator reconfirmation. Give the T3 coordinator and interactive operator distinct credentials. Project roles start with **observer** (status, metadata and bounded job events), **runner** (plus create, guest execution, transfer and stop within quotas) and **operator** (plus policy decisions, retention and guest terminal). Grant terminal access explicitly to a runner when needed. Host credentials, engine selection policy and pairing administration stay with the host operator.

Require project/resource authorization for every route, including job status, events, downloads and terminal tickets. A request can ask for a narrower capability than its credential or profile grants. Registering a new profile, adding a credential and granting egress are separate operator actions. Accept neither physical host paths nor upstream URLs for credential use from an agent.

## 5. Engine, network and agent contracts

**Engine registry.** Select by explicit engine ID, supported version and operator-approved profile. At startup, `probe()` reports effective capabilities for this host. On create, persist the selected engine, version, image digest, external VM identifier, launch generation and Alpi ownership marker. On recovery, use the recorded adapter and verify identity before attach, stop or deletion. An unavailable engine produces a typed diagnostic. A second engine can run alongside the first for newly created sandboxes. Migrating a running machine across engines is a separate operation.

| Adapter surface | Contract exercised by the daemon |
| --- | --- |
| `probe / create / inspect / start / stop / destroy / listOwned` | Idempotent create with an Alpi allocation ID, discoverable ownership marker, explicit resource limits and observable terminal state |
| `exec / readFile / writeFile / attachPty` | Argument arrays, guest cwd, bounded streams, exit status, deadlines, cancellation and optional interactive PTY |
| Network attachment | Prepare a host-enforced denied state before guest code starts. Bind only the sandbox’s assigned relay. Report health and fence the route on fault. Release resources after verified stop |
| Optional capabilities | Persistent disk, PTY, exportable snapshots and cloning are advertised separately. Unsupported requests fail before allocation |

Implement a deterministic fake adapter for the contract suite, then BoxLite as the first real adapter. Prefer its local SDK in a supervised helper so the network context of its VM and outbound networking process can be controlled. Test this topology before committing to its packaging. Keep the engine administration endpoint private. Run the same contract suite against Microsandbox as a later independent adapter, including the network and lifecycle tests. A passing fake proves dispatch semantics only. [BoxLite](https://github.com/boxlite-ai/boxlite) · [Microsandbox](https://github.com/superradcompany/microsandbox)

**Iron and local inference.** Give each networked sandbox a host-side network boundary, an Iron instance or equivalently isolated policy context, a sandbox-bound callback and a credential relay. A concrete Linux design to validate is a per-sandbox network namespace containing the BoxLite helper/network stack, with only a route to that sandbox’s fixed relay endpoints. The privileged setup helper accepts typed operations for owned resources. The API daemon runs as a dedicated service account. Keep the management API, engine control, callback, vault and other sandboxes outside the guest’s reachable network. BoxLite documents host-loopback access through its built-in alias. Allowing that alias alone is insufficient to isolate an individual proxy port. If the selected release cannot confine the networking process, keep that adapter’s networked profile unavailable and evaluate the other adapter explicitly. [BoxLite networking](https://github.com/boxlite-ai/boxlite/blob/main/docs/guides/networking.md) · [Current Alpi boundary](../SECURITY.md)

Start network service in this order: reserve capacity and deny-by-default attachment, prepare Iron and callback, verify identity and policy readiness, then enable only the assigned relay. Guest proxy variables and its CA bundle support applications. The host enforces reachability even for guest root. A proxy failure closes egress and keeps the management channel available for diagnosis. Recovery verifies ownership and policy before reopening. Headless operators pre-authorize exact destinations or resolve a bounded pending request through the CLI. Timeout denies the request. Grants carry project, sandbox scope and expiry.

For local inference configure a named, operator-owned destination and its allowed model/API routes. The host relay can reach a specifically configured local service or approved upstream, including an unauthenticated one. Keep general access to host and LAN services closed. Validate the dedicated local route against Iron’s existing loopback/private-address protections. If a loopback inference service requires a connector, place a fixed-destination connector downstream of the approved Iron route. Verify that only the designated endpoint is reachable. Certify this topology before advertising that profile. Use synthetic credentials during integration. For real provider secrets, the Linux reference implementation reads service credentials supplied by `LoadCredentialEncrypted=` via a vault interface. The current Keychain adapter remains Mac-specific. [Linux service credentials](https://www.freedesktop.org/software/systemd/man/250/systemd-creds.html) · [Alpi credential bridge](../src/runtime/credential-bridge.cjs)

**Harness adapters.** Keep `harness`, `provider` and `model` as separate job fields. Each installed harness advertises supported session operations: create/resume, submit, observe, steer, cancel and interactive join. Store its native session ID separately from the Alpi job ID. Implement a shell fixture and Pi for the first live job. Qualify OpenCode against the same job contract as the second harness. Make external providers opt-in. Provider credentials and the GPU/model server stay outside the guest. Limit simultaneous inference requests separately from VM count. Direct interactive input and coordinator steering share a single writer lease. Additional readers can follow events.

## 6. The v1 API and durable behavior

Use one versioned API with a checked-in OpenAPI contract. CLI and MCP both call it. Negotiate protocol and capabilities before a mutation. Use UTC timestamps, opaque IDs and machine-readable error codes. Limits on vCPUs, RAM, disk, running sandboxes, job duration, transfer sizes and retained storage come from the host and project. Admission and reservation are atomic, including parallel requests. Return a capacity error with retry guidance.

| Resource and operation | First-release result |
| --- | --- |
| `GET /v1/capabilities` | Authenticated server identity/version, permitted engines, pinned profiles, harness/model choices, limits and attach modes |
| `POST /v1/sandboxes` and `GET /v1/sandboxes/{id}` | Create with engine/profile, resources, retention and TTL. Return a sandbox ID and asynchronous state. List within the authorized project |
| `POST /v1/sandboxes/{id}/start`, `/stop` and `DELETE /v1/sandboxes/{id}` | Start, stop with disk retained, or explicitly destroy after checking ownership, retention, export and concurrency preconditions |
| `POST /v1/artifacts` and `GET /v1/artifacts/{id}/content` | Bounded upload/download with content digest and project ownership. Temporary objects expire. Publish only complete, verified content |
| `POST /v1/sandboxes/{id}/imports` and `/exports` | Copy from an artifact into a fresh guest workspace, or export selected guest files to a new artifact. Receipts include content root, size and digest |
| `POST /v1/sandboxes/{id}/jobs`, `GET /v1/jobs/{id}`, `/events?after=…`, `POST …/messages` and `…/cancel` | Submit, reconnect to bounded ordered events, steer and request cancellation. Report sequence gaps, pending actions, native session ID and observed exit state |
| `POST /v1/sandboxes/{id}/exec`, `…/terminal-tickets` | Guest-only command invocation or short-lived, single-use ticket for an authenticated PTY stream. Allow a human to join the running harness session when the adapter supports it |
| Operator CLI on the private admin socket | Issue and revoke invitations/clients, inspect status, resolve network requests, inspect storage and drain a host. Every decision records principal, project, sandbox and outcome |

Example proposed creation payload:

```json
{
  "engine": "boxlite",
  "profile": "pi-dev",
  "resources": { "vcpus": 2, "memoryMiB": 2048, "diskMiB": 8192 },
  "retention": "until-export",
  "ttlSeconds": 3600
}
```

**Recovery and persistence.** Use a single-host transactional store such as SQLite on local disk for pairings, roles, jobs, request receipts, leases and reservations. Record mutation intent before engine or guest side effects. Scope an idempotency key to the principal, project and operation, and bind it to the request fingerprint. Exact retry returns the original receipt. Conflicting reuse returns 409. A lost engine reply triggers reconciliation by allocation ID. A lost non-idempotent guest reply becomes `uncertain` until observation or operator resolution. Reconnecting an MCP client must never start a duplicate job.

Persist desired state and observed state separately. Creation proceeds from reserved to provisioning to ready or failed. Stop retains the disk. Destruction has its own durable pending state. Reconcile on daemon restart using engine identity, launch generation and ownership markers. Release capacity only after observing the terminal state. Model job cancellation as a request followed by observed termination, with an explicit unknown state when the harness cannot prove it. Retain the workspace and evidence on unexpected failure.

Provide an ephemeral profile with an expiry and a persistent interactive profile with an idle-stop policy. At expiry, fence new execution and stop the VM. For `until-export`, retain the disk until a verified artifact exists and the client acknowledges receipt, or the operator explicitly discards it. Report retained bytes and block admission at quota. Deleting a VM never deletes acknowledged project artifacts implicitly. Retain T3/Pi session state and the checkout together for the interactive case. Resume after service restart is distinct from restoring process memory. Record capabilities accordingly.

**Transfers over a remote connection.** The client reads an explicitly staged source tree on the laptop, preferably from a known Git revision plus deliberately selected local changes. The Linux server receives bytes. Its host home and filesystem paths are inaccessible through this interface. The client similarly chooses the export destination in an allowed project directory. Validate byte/file limits, entry types, normalized relative paths and digests before publishing. Import/export directory receipts expose the actual content root. Keep stale upload chunks and interrupted exports identifiable and reclaimable. Never execute an export as part of collection.

## 7. MCP, skill and interactive access

The portable command `alpi mcp --context gaming-pc` runs on the machine that hosts the **outer T3 provider**. It loads the operator-created context, opens the authenticated API connection and serves stdio MCP. The service continues to run when the MCP subprocess exits. Register it under a distinct name such as `alpi-server` so the existing local `alpi` connector remains usable. Configure the provider profile selected in T3. A per-provider MCP registration should be tested in both that T3 profile and standalone Codex.

```sh
codex mcp add alpi-server -- /absolute/path/to/alpi mcp --context gaming-pc
```

Publish tools for capabilities, sandbox create/list/inspect/start/stop, project upload/import, job submit/status/wait/send/cancel, guest exec and export/download. Scope tools to the context. Keep deletion explicit, with resource identity and a separate permission. Human terminal attachment and pairing use CLI commands. Each tool returns structured IDs, status, retry semantics and receipt data. Filter control credentials, raw provider responses and guest-supplied URLs from status. Label guest-produced text and files as untrusted inputs to the coordinator.

Write `skills/alpi-server/SKILL.md` around one real workflow. Select the named host, engine, harness and model from capabilities. Stage the repo, create/import, record sandbox/job/request IDs, wait using a cursor, handle a pending operator action, verify guest tests, export and inspect the diff, then apply the requested retention policy. Include reconnect, uncertain submission and cooperative cancellation. Skill selection documents user intent. The server independently enforces permissions. A human can use `alpi terminal <sandbox-id>` or `alpi attach <job-id>` with an authorized context. The latter joins the same harness conversation if advertised.

## 8. Implementation sequence

| Slice | Depends on | Deliverable and exit condition |
| --- | --- | --- |
| 1. Repository and distribution | Current checkout | Independent server/client commands, production lockfiles, service unit, Linux manifest resolver, package inventory and installer tests. Install from release artifacts on a disposable Linux system, with stock Iron acquired from the official release and its identity verified. Run the existing portable desktop tests against the same commit. |
| 2. Pairing and API skeleton | 1 | Durable server identity, private admin socket, TLS, invite exchange, project credentials, revocation and authenticated capabilities. Ship a capabilities-only stdio MCP in the first package cut. Pair the existing T3 installation with the separate PC and read its server ID and installed runtime inventory before agent support lands. Cover expired/consumed invites, concurrent exchange, identity mismatch, revoked streams and cross-project isolation. |
| 3. Engine and Iron qualification | 1, in parallel with 2 | Registry, fake conformance fixture, BoxLite helper and isolated network attachment. On real KVM, boot two unique VMs. From each, prove access to its own allowed test destination and denial of direct egress, host services and the peer. Interrupt Iron/callback and verify the guest loses egress while host-side control remains available. This is the decision point for the first engine. |
| 4. Workspaces, jobs and recovery | 2, 3 | Quotas, persistent registry and leases, imports/exports, Pi and shell fixture, local-model relay, typed errors and lifecycle recovery. Repeat a create after a lost reply, restart the service during a synthetic job, cancel a long-running fixture, reopen a retained checkout and verify its identity. |
| 5. T3 client experience | 2, 4 | Extend the already paired CLI and MCP to the full job lifecycle. Ship the `alpi-server` skill and interactive attach. Drive the full flow from the existing T3 installation. Detach the laptop, reconnect to the same job and verify the returned diff and test output. |
| 6. Full Linux pilot and release | 1–5 | Execute the two-machine runbook below from built packages. Publish the compatibility matrix, sanitized acceptance evidence, measured performance and rollback instructions with the release candidate. |
| 7. Follow-on compatibility | First pilot accepted | Qualify OpenCode as a second harness and Microsandbox as a second real engine with the same fixture and API. Qualify T3 headless as a persistent guest profile. Add Alpi Desktop remote pairing against the established API in a later delivery. |

At slice 3 record the chosen engine version, the Linux mechanism enforcing network restrictions and any unsupported features. If BoxLite cannot meet the required boundary, use the same fixture to evaluate Microsandbox and record the operator’s engine choice. Do not certify a backend on the basis of a feature list or a successful VM boot.

## 9. Two-machine acceptance runbook

The commands below describe the operator experience to implement. Use a disposable sample repository, a non-production model route and a new project. Record release and profile digests, OS/kernel, CPU, RAM, storage type and KVM access. Keep invitation and credential values out of the record.

1. **Install on the gaming PC.** Install the lightweight server package, initialize the service account and state, then check KVM access, memory, disk, the chosen network mechanism and systemd credentials with `alpi-server doctor --host`. Run `alpi-server runtime install --engine boxlite --profile pi-dev`, configure the inference route and verify the selected artifacts using `alpi-server doctor --runtime`. Start the service. During pilot acceptance, verify its health after an operator-scheduled host reboot. Package installation performs privileged setup explicitly. The runtime daemon runs with the narrower grants it needs.
2. **Pair this T3 installation.** Issue a runner invitation for the pilot project through the Linux console. On the machine running the T3 provider, install the client and run `alpi pair --name gaming-pc`. Register the stdio connector and load the skill. Verify the tools from a provider session in this T3 installation, reloading that session if discovery is tied to startup. Confirm the returned server ID matches the Linux console and the chosen engine is available. Pair a separate interactive operator context.
3. **Complete real work.** From T3, create sandbox A, upload the sample repo, use the receipt’s content root and ask Pi to make a small change with a matching test using the selected local model. Confirm a second sandbox B can run an independent build and sees only its own files. Disconnect the client. Reconnect, identify the original job by receipt, and follow its events. Enter sandbox A with the operator context, take interactive control of the same session, then return control to the coordinator.
4. **Collect and clean up.** The outer coordinator runs the relevant tests in the guest, retrieves the patch and test report, verifies hashes and inspects the actual diff. Stop and restart a persistent sandbox and verify the checkout and conversation. Destroy only the disposable owned instances after collection, check resource reclamation, then revoke the pilot credential and verify a subsequent call is rejected.
5. **Measure the user-visible workflow.** Separate initial install/image pull, cold creation, cached creation-to-first-successful-guest-command and time to accepted result. Capture p50/p95, whole-host idle memory, incremental active memory, disk growth/reclamation and peak concurrent model requests. Start at concurrency 1, then 4 and 8 only within measured capacity. Record sample counts and failures. Set performance targets for this machine from the first baseline. Isolation, identity, recovery and correct results are release criteria on the first run.

**Done for the first release:** installable Linux server and client packages, official component manifests, authenticated pairing and revocation, a real KVM adapter passing the Iron boundary tests, a complete T3 → remote guest → verified artifact run, a working human attach path, independently checked persistence/recovery and usable MCP/skill instructions. Track untested platforms and optional capabilities explicitly. Packaging, unit fixtures and the current Mac tests provide separate evidence from this live PC run.
